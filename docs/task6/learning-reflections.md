# Task6 学习心得：把调度与执行分开

Task5 的委派解决了职责划分，Task6 进一步要求我考虑等待期间的体验。一次工具调用能返回任务 ID，只说明启动请求完成；后台任务是否已经执行、是否排队、是否失败，要继续查运行服务。主 Agent、Agent Server、LangSmith 分别承担交互决策、任务执行和追踪分析，理解这三个角色后，排障方向清楚了很多。

我最重视的验证是：后台任务仍在运行时，主 Agent 能否回答一个无关的简单问题。单看启动耗时容易把模型生成的延迟、网络请求和子任务耗时混在一起。把主线程响应与服务端 run 状态放在同一条记录中，才能说明这次调用确实没有等子任务完成。

任务 ID 与 run ID 的区别也很实用。追加指令保留子任务 thread，但会创建新 run；旧 run 被打断。取消后再次 update 可以延续会话历史，却不意味着恢复一个暂停中的 Python 协程。如果业务有文件写入、发信或扣费等副作用，还要另外考虑幂等与补偿，取消本身不会撤销已经发生的操作。

Skills 让我把“Agent 有哪些能力”和“当前任务需要哪些详细规则”分开组织。description 要写清触发场景，正文要写成可执行步骤，长规则放到 references。验收时应检查模型第一次请求、实际 read_file 和生成的文件，才能确认渐进式披露发生了。启动时解析文件不等于把整份正文交给模型。

以后设计 Agent，我会给每个能力明确输入、产物位置与验收条件；给后台任务保留 thread/run 的关联；给 Skills 设置清晰的触发描述。模型说“完成”只是交互的一部分，实际状态和落盘产物仍需要核对。
